# SnapIt — notes for coding agents

Screenshot app for macOS and Windows. UI is [gpui-kit](https://github.com/longbridge/gpui-kit) on Zed GPUI. Capture freezes every monitor, opens one borderless overlay per display, then copy / save / OCR / GIF / pin.

Do not bump `gpui-kit` or the Rust toolchain without an explicit request. Prefer extending existing crates over rewriting the MVP.

`vendor/xcap` is a git submodule (fork `gjfei/xcap`) added to the workspace `exclude` and consumed as a path dependency, so changes made there need their own commit inside the submodule plus an updated gitlink in this repo. Clone with `--recursive`; CI/release checkouts must use `submodules: recursive`.

User docs: `README.md` (Chinese) and `README.en.md` (English) mirror each other — update both together. `CLAUDE.md` only points here.

## Crate map

| Crate | Path | Role |
| --- | --- | --- |
| `snapit-capture` | `crates/capture/src/lib.rs` | `xcap` multi-monitor capture, monitor-unit geometry, crop, PNG/JPEG, window enumeration (`windows.rs`) |
| `snapit-recorder` | `crates/recorder/src/lib.rs` | Region GIF/MP4 (`vendor/xcap` live frames + `gif` / AVFoundation / Media Foundation; frame dedupe, duration cap, pause, discard, optional cursor). macOS asks ScreenCaptureKit to deliver the selection's logical size directly (`OutputSize::Logical`); `video::prepare`'s integer box mean stays as the fallback on Windows and whenever the hint is ignored; GIF uses a shared NeuQuant palette, a lazy 6-bit RGB LUT and dirty-rectangle partial frames; MP4 keeps the scaled frame for its closing sample. An extended-range session records HDR10 HEVC Main10 (see the HDR recording invariant) through `video/{hdr,macos,windows,mp4_colour}.rs` |
| `snapit-ocr` | `crates/ocr/src/lib.rs` | `OcrEngine` trait; Vision / ocrs / Windows.Media.Ocr |
| `snapit-store` | `crates/store/src/{config,history,paths,fs}.rs` | TOML settings, history index, `AppDirs` |
| `snapit` (bin) | `crates/app/src/main.rs` | gpui-kit shell |

App modules (`crates/app/src/`):

- `controller.rs` — global workflow: freeze → overlay → copy/save/OCR/GIF/pin
- `session.rs` — frozen frames, region selection (single, or hold `Shift` to collect several; releasing combines same-display regions into one selection), `SessionCommand` / `CaptureIntent`, window-snap hover/click (`capture.window_snap`)
- `annotate.rs` — overlay annotation model, GPUI canvas paint, tiny-skia bake
- `overlay.rs` — fullscreen selection UI + toolbar (`F` full display, `C` copies the pixel color, hold `Shift` to collect regions); the toolbar can be dragged and keeps that position; turns into the recording outline after the region is committed
- `recording_bar.rs` — in-recording control bar: icon-only pause/resume, cancel (discard) and stop (save) buttons, plus the timer (`BAR_SIZE` 312×44; window equals the visible card; opens before the recorder's first frame and shows 准备中); tooltips / accessibility labels carry the button names; draggable via the native window drag (`start_window_move` on macOS, `WM_NCLBUTTONDOWN` on Windows)
- `pin.rs` — always-on-top pin windows
- `tray.rs` — resident tray menu
- `settings.rs` / `settings_view.rs` — live `Config` + settings window
- `history_store.rs` / `history_view.rs` — history entity + UI
- `hotkey.rs` — global shortcut parsing / validation and OS registration (`global-hotkey`); pressed events are delivered by `events.rs`
- `events.rs` — one event bus: `set_event_handler` callbacks from `global-hotkey` / `tray-icon` (platform threads) plus forwarded launch requests all post `AppEvent`s into an unbounded channel, drained by one `cx.spawn` task on the GPUI main thread
- `i18n.rs` — UI locale resolution (`general.language`: `auto` / `zh-CN` / `en`)
- `ocr_view.rs` — small OCR results panel (opened after region OCR; not a launcher)
- `updater.rs` / `update_view.rs` — GitHub Releases check (pre-releases included), download + SHA-256 verify, Windows install / macOS disk-image hand-off, update window (`[update]` in `config.toml`)
- `appearance.rs` — theme + macOS Dock / Accessory (Dock icon only while a panel window is open)
- `clipboard.rs` — shared clipboard writes: image data (PNG / GIF) and file references (`FileCopy::File` vs the `PathText` fallback)
- `instance.rs` — single-instance file lock + launch-request forwarding (`snapit.lock` / `snapit.request`); the only remaining 50 ms poll, because a file has no notification mechanism
- `autostart.rs` — launch at login (`--background`; same tray-only as default launch)
- `assets.rs` — extra Lucide icons (`Crop`, `Pin`, `Images`, …)

OCR backends: `crates/ocr/src/vision.rs` (macOS), `ocrs_engine.rs`, `windows_ocr.rs` (Windows.Media.Ocr).

Recording pipeline: `snapit_capture::LiveRecorder` wraps `xcap::VideoRecorder` with `VideoRecorderOptions` (`vendor/xcap/src/video_recorder.rs`): region in monitor units, fps cap, a cursor flag, a `DynamicRange` request (only HDR MP4 sessions ask for it; the platform may still deliver SDR), own-window exclusion, an `OutputSize` hint (`Logical` asks macOS's compositor for the selection's point size; DXGI ignores it), and frames (`FrameData::Sdr` / `Hdr`) stamped with `Duration` since the recorder was created. macOS uses ScreenCaptureKit (`SCStream` with a `sourceRect` and output dimensions in physical pixels, or in that rectangle's own point size when `OutputSize::Logical` is requested so the compositor downscales before the callback; no post-crop is needed) and excludes SnapIt's own windows by filtering the process's `SCWindow`s out of the `SCContentFilter`; this path needs macOS 13 because the framework is linked strongly. Windows crops in the DXGI sender thread and throttles there. `Recorder::start` blocks until the first live frame (5 s timeout) so the UI timer and the sink share an origin, then creates the GIF/MP4 sink on that frame's real dimensions. The recording outline re-uses the recorded display's overlay window (`OverlayView::enter_recording`); the bar and that window both call `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` on Windows.

App mark: `assets/snapit-icon.png` (1024), `assets/snapit-tray-template.png` (menu-bar template), `assets/AppIcon.icns`, `assets/snapit.ico` (Windows exe/window icon; `crates/app/build.rs` embeds it as resource 1, which gpui-pre-windows loads for every window and Explorer shows on the exe).

Diagnostic logging: `crates/app/src/logging.rs` is the app's single global `log::Log`; it fans every `log::*` record out to stderr (Info+) and a rotating file at `AppDirs::log_file()` = `<data_dir>/logs/snapit.log` (Debug+, rotated to `snapit.log.old` at 8 MiB). Because it hooks the `log` facade, logs from all crates — including vendored `xcap` — reach the file with no extra deps; do not add a second logger or reintroduce `env_logger`. startup: `logging::init(&dirs.log_file())` in `main.rs`, after `dirs` is resolved. Each capture/record calls `logging::begin_capture()`/`begin_recording()`, which publish a monotonic id into an atomic slot; the logger stamps every line with `[cap#N]` / `[rec#N]` (or `[-]` when idle) so one operation's whole chain is grep-able: `grep '\[cap#12\]' snapit.log`. `RUST_LOG` overrides the file level (default `debug`). For post-mortem HDR issues, the decisive lines are: HDR candidates + potential/current EDR (`capture::hdr_candidates`), per-display `HDR capture OK/NotSupported/failed`, `HDR frame ... has_highlights`, and `HDR export declined/...` (`session::export_hdr`), `save branch`, `encoding HDR PNG ... cICP`, plus `xcap macOS/Windows HDR:` lines from the platform capture. No screen interaction is needed to read them.

## Hard invariants

- **gpui-kit `=0.9.1`** in the workspace `Cargo.toml`. It pins GPUI (`gpui-pre` 0.3.12). Do not float the version.
- **Rust 1.99.1** via `rust-toolchain.toml` (edition 2024).
- **Log every capture/record decision point.** Real users (and CI on other OSes) have no console, so diagnosis is post-mortem from `logs/snapit.log`. Any new branch that can change what pixels/format get captured or saved — HDR candidate selection, platform capture fallback, highlight decision, export veto, sink selection — must emit a `log::info!` (or `warn!` on failure) with the deciding values. Do not reintroduce temporary `/tmp` probe files; use the persistent logger with its automatic `[cap#N]`/`[rec#N]` tag.
- **BGRA for `RenderImage`.** Captures are RGBA; `session::render_image` swaps R/B before GPUI. Reuse that helper; do not feed RGBA frames to `img()`.
- **Window coordinates.** Overlay/pin `WindowOptions` must set both `display_id` and `window_bounds` from GPUI `PlatformDisplay::bounds()` (overlay slots from `SessionSlot`). macOS bounds are per-display (origin often `0,0` on that screen). Windows bounds are the global virtual desktop. Do not place windows from raw `xcap` `MonitorInfo::{x,y}`.
- **Overlay pre-placement (macOS only).** The overlay windows are created while the freeze runs on a worker: `CaptureSession::new` starts with one `SessionSlot` per display and no frames, then `set_frames` matches captured monitors to slots and fills them. Pre-placed windows use `window_background: Transparent` and an empty frame, so they contribute nothing to the freeze. On macOS they are created with `show: false` and then ordered front at zero alpha (`overlay::pre_place` → `setAlphaValue: 0`, `ignoresMouseEvents`): GPUI warms the surface during the freeze, but AppKit's opaque default background never shows. `OverlayView::activate` restores alpha 1 only after the next rendered frame (`Window::on_next_frame`) — revealing an undrawn fullscreen layer flashes black — then makes the window key. A Windows window with `show: true` is on screen before its first transparent frame, so Windows opens overlays with the frames already set instead of pre-placing them.
- **xcap units.** `snapit_capture::Region` is in *monitor units* (points on macOS, physical pixels on Windows). Images are always physical pixels; use `Screenshot::pixels_per_unit` / `SessionFrame::to_region`.
- **`WindowKind::PopUp`** for overlays, recording bar, and pins (always-on-top, no titlebar chrome).
- **The recording region re-uses the capture overlay; the bar is its own plain `cx.open_window`.** Closing the overlay and opening a second frame window made the selection border blink away during the hand-off, so recording keeps the recorded display's overlay and turns it into the live indicator: `Controller::start_recording` takes that window out of `ActiveSelection` (closing the other displays' overlays), then `OverlayView::enter_recording` drops the frozen frame and toolbar and paints `recording_frame` — the same look as the selection stage, the viewport dimmed with `theme.overlay` outside the region plus a 1 px `theme.primary` border — and makes the window click-through (`ignoresMouseEvents` on macOS; `WS_EX_TRANSPARENT | WS_EX_NOACTIVATE` on Windows), and the recorder leaves it out of the frames (own-window exclusion in ScreenCaptureKit on macOS, `SetWindowDisplayAffinity` on Windows). The mask and border are drawn outside the captured bounds, so the file never contains them. `gpui_kit::open_window` wraps the view in `gpui_base::Root`, whose window-state plugin paints `theme.background` on the whole surface, so `enter_recording` overrides `Root`'s own background with `transparent_black` — that refinement is applied after the plugin styles; that is why the display-sized layer does not black out the screen. Recording starts only after the window has presented a frame with the live content (`Controller::after_presented_frame`, two `on_next_frame` steps because callbacks run before the frame is drawn); otherwise the first recorded frame would still show the frozen overlay. The recording bar is opened right away in a "starting" state (`ActiveRecording.started = false`, `recording.starting`), and the recorder joins the same state when its first live frame lands, so the bar does not wait for `Recorder::start`. Stopping during that window cancels: `stop_recording` clears the session, and `spawn_recorder` stops the recorder it was handed on a worker thread and deletes the empty file. The bar window is exactly `BAR_SIZE` with no transparent margin — a margin exposed the system window's own border around the card — and keeps using plain `cx.open_window`, because an opaque Root card would paint the corners. `Esc` / the bar's Cancel button **discards** instead of saving: `Controller::cancel_recording` closes the bar and outline right away, then `Recorder::discard` joins the sinks on a worker thread and deletes the `.part` file (no history entry, no clipboard write, no notification); cancelling during the warm-up window leaves the same cleanup to `spawn_recorder`. `Space` / the pause button calls `Recorder::set_paused`: the capture thread keeps draining platform frames but encodes none of them, and `PauseClock` subtracts paused stretches from the frame timeline, `Recorder::elapsed` and the duration cap. Stop / `Enter` / a global hotkey still saves.
- **Publish a finished recording, and copy it, before the bar closes.** `recording_paths` starts the recorder on a `.part` file inside the save directory (falling back to the temp directory when a write probe fails), so finishing is a same-directory rename instead of a copy out of `$TMP`. The probe is a throwaway `.probe` sibling: AVAssetWriter refuses to open an existing file, so the recording path itself must not be pre-created. `stop_recording` then fills the clipboard (GIF bytes / MP4 file reference) and only afterwards calls `finish_recording_ui` and posts the notifications — the bar closing is the completion signal, and a paste right after it must never find empty or previous clipboard content. The history copy and thumbnail run detached after that, and both the encoder poll and the capture loop's `recv_timeout` are 4 ms: they are the only latency between the stop click and the clipboard, while 0 ms would busy-wait a whole core.
- **Hide selection overlays before destroying them (macOS).** Tearing down a fullscreen GPUI overlay costs ~37 ms on the main thread (renderer/Metal layer drop), which used to sit between the copy command and the clipboard write. `close_selection` now calls `overlay::hide` (`NSWindow orderOut:`, instant) and queues the handles in `Controller::pending_close`; `finish_pending_close` does the real `remove_window` after the clipboard/file write lands (in `copy_image` / `save_image` completion, or synchronously for commands with no late work). Windows has no cheap hide and keeps the synchronous removal. Every path that hides must eventually flush or the window leaks — `abort_capture`, the overlay-failed branch and the save-dialog-dismiss branch all flush explicitly. The 37 ms teardown still happens; it is just off the paste path.
- **Recorder start is probe-free; stop overlaps the sink flush.** A screenshot probe at `Recorder::start` used to cost 9–13 ms on every recording only to surface a permission error; `snapit_capture::screen_recording_granted` (macOS `CGPreflightScreenCaptureAccess`, other platforms `true`) replaces it, and the fallback capture is now taken lazily only when the recorder delivered no frame at all. On stop, `sink.finish` runs on a scoped side thread while the capture thread calls `live.stop()` (saves ~4–10 ms); only the `FrameSink: Send` crosses threads — `LiveRecorder` holds Objective-C objects and must stay put. Fork-side SCK enumeration uses `excludingDesktopWindows:true, onScreenWindowsOnly:true` in both `impl_video_recorder.rs` and `hdr.rs` (hot p50 18.4 → 2.7 ms) and is a separate commit on the still-open HDR PR branch.
- **Close recording windows with `cx.defer`.** `finish_recording_ui` is often reached from the bar's own key/click handler, and GPUI takes a window out of `App::windows` while that window is on the update stack: `handle.update(... remove_window())` then returns `window not found` and is silently swallowed by `.ok()`, leaving a bar stuck on `recording.finishing` ("正在结束…"). Removing the handles in a deferred effect runs after the stack unwinds; `RecordingBar::render` also paints nothing when `Controller::has_recording()` is false, so an orphan window can never show that fallback label.
- **GIF encoding is palette + LUT + dirty rectangles, never per-frame `Frame::from_rgba_speed`.** The latter rebuilds NeuQuant and hashes every pixel (~170 ms/frame at 1000×600). `PaletteMap` trains on a sparse spatial sample and fills the 6-bit RGB LUT lazily — eagerly resolving all 262,144 bins cost ~50 ms per palette, while a screen recording only visits a fraction of the RGB cube. `dirty_rect` plus `DisposalMethod::Keep` means LZW only encodes the changed rectangle; a static frame still writes a 1×1 frame so its delay survives, and a palette refresh forces a full frame because every index changes meaning. `color_quant` is a direct dependency because `gif` pulls the same version; `RecordOptions::quality` controls the training sample count.
- **Downscaling is `video::box_downscale`, not `image::imageops::resize(Triangle)`.** Retina frames arrive in physical pixels while the selection is in logical points, so both sinks share a 2× integer area-average downscale. Triangle cost ~13 ms/frame in release (~44 ms in test builds) versus ~4 ms for the box mean. Since 2026-11-15 macOS can skip it entirely: `VideoRecorderOptions::output_size` (in the `gjfei/xcap` fork, PR `feat/video-recorder-region-options`) takes `OutputSize::Logical`, which sets `SCStreamConfiguration.width/height` to the `sourceRect`'s point size so ScreenCaptureKit scales in the compositor and the whole pipeline sees a quarter of the pixels on a 2x display. The option is an enum, not a pixel number: callers only know the region in monitor units, so stating "logical size" keeps the Retina scale factor inside the platform layer and needs no aspect-ratio derivation — the height is already the region height. `scalesToFit = false` keeps the frame from being letterboxed. **Keep the hint optional and keep `video::prepare` as the fallback**: DXGI has no equivalent and ignores the option. A device A/B on 2026-11-15 (2x Retina, 800×500 logical region, a pattern window with four corner markers, multi-size text, a 1 px grid and a flat cursor zone) showed that SCK scales the whole `sourceRect` rather than cropping its top-left quarter (MAE 2.3/255 vs a box-downscaled native frame, 39.4/255 vs a 1:1 crop), keeps the cursor proportional (11×17.5 vs 10×15 logical px, origins aligned), and softens fine detail: edge energy −9.6% on text and −35% on the 1 px grid versus the CPU box mean. `SNAPIT_CPU_DOWNSCALE=1` forces the old CPU path on the same build when hairline sharpness matters; frames are otherwise near-identical (MAE 2.3/255). Fork changes go on the still-open PR branch as one independent commit; never rebase a pushed PR branch or let another PR's commits leak into it, and update the submodule gitlink in this repo.
- **HDR stills are opt-in per monitor, and the SDR path stays the default.** `xcap`'s `HdrImage` is half-float scRGB (1.0 is the SDR reference white: 203 nits on macOS, 80 on Windows). `snapit_capture::hdr_candidates()` decides where the extended-range capture is even tried: on macOS it reads `NSScreen.maximumPotentialExtendedDynamicRangeColorComponentValue` (the current-headroom value is process-scoped) and therefore **must run on the main thread** (called from `Controller::start_capture_now`, before the freeze worker starts); an SDR panel, macOS 13/14 and Intel Macs are never routed through ScreenCaptureKit, which keeps the freeze on the existing fast CG path. Elsewhere every monitor is a candidate and the platform returns `NotSupported` cheaply (DXGI checks the output color space before creating a device). `xcap`'s macOS HDR capture needs ScreenCaptureKit's macOS 15 HDR screenshots (Apple Silicon only; the API is resolved at runtime, so the 13.0 deployment target is unchanged); Windows needs `IDXGIOutput6`/`DuplicateOutput1` with `R16G16B16A16_FLOAT` scRGB or `R10G10B10A2_UNORM` HDR10. A successful capture replaces the SDR frame with `HdrImage::to_sdr()` for the overlay, and the `HdrImage` is kept only when `has_highlights()` — an HDR display showing SDR content still saves ordinary 8-bit PNG. Windows HDR composites SDR windows at the user's SDR brightness (`DISPLAYCONFIG_SDR_WHITE_LEVEL`, ~200 nits by default), so DXGI capture records SDR white well above scRGB's 80-nit unit: the Windows capture calls `HdrImage::with_sdr_white()`, `has_highlights()` compares against that level instead of 1.0, and `to_sdr()` divides by it so the preview matches an SDR grab. macOS extended sRGB already uses SDR white as 1.0, so its default threshold is unchanged. The Windows gate accepts only the two encodings the fork decodes — full-range scRGB (`RGB_FULL_G10_NONE_P709`) and full-range PQ BT.2020 (`RGB_FULL_G2084_NONE_P2020`); studio-range and YCbCr desktop modes keep the SDR grab rather than write a wrongly converted 16-bit file. The decoder is chosen per frame from the delivered texture format (DXGI converts the desktop into the requested format, and the duplication description reports the display mode rather than the converted surface), and rotated displays fall back to the SDR grab: `AcquireNextFrame` always returns the unrotated surface with the image rotated inside, which cannot be mapped onto the selection without a rotate step GDI already does. Save writes the HDR pixels as a 16-bit RGB PNG with a `cICP` chunk `[9, 16, 0, 1]` (BT.2020 primaries, PQ transfer, identity matrix, full range), converting scRGB to BT.2020 and nits via `reference_white_nits()`; the PQ table is indexed by `sqrt(nits / 10000)` so sub-nit steps stay precise. `CaptureSession::export_hdr()` refuses composed, multi-region and annotated selections because annotations bake in 8-bit.
- **Save, Copy and history originals are the same pixels.** When an HDR frame exists, all three durable stills are the 16-bit BT.2020/PQ PNG with cICP `[9,16,0,1]` — not a tone-mapped 8-bit SDR copy. `handle_command` exports HDR for every image-producing command (Copy/Save/Pin/Recognize) and stores it on `Captured { image, hdr, scale }` (`Arc` in both, so clones are cheap); `image` is only the SDR view for overlay/pins/OCR/thumbnail. `save_image` writes `hdr` to the file; `copy_image` writes `encode_png_hdr(hdr)` bytes — GPUI's `ClipboardItem::new_image` copies PNG bytes verbatim on both macOS (`public.png`) and Windows (registered `PNG` format), so the 16-bit payload is not decoded or downgraded; `remember`/`HistoryStore::add_image` encodes the same `hdr` off-thread and stores it as the history original via `NewEntry::image_hdr`, with `HistoryEntry.hdr: bool` (`#[serde(default)]`, so old index entries read as SDR) marking the file. The history thumbnail stays 8-bit SDR for the UI. Re-opening an HDR history original for a pin goes through `snapit_capture::decode_hdr_png_preview` (PQ EOTF + inverse BT.2020 matrix, 203-nit reference white) instead of `image::to_rgba8()`, which would misread 16-bit PQ samples as linear sRGB. GIF/MP4 recordings are unrelated and still use SDR stills/video unless the recording HDR path applies.
- **HDR recording is HDR10 in MP4, requested per session and gracefully falling back to SDR.** `[recording] hdr` (default true) only changes MP4 recordings: GIF stays SDR. The capture thread asks `xcap` for `DynamicRange::Hdr`; that is a request, not a guarantee — macOS only routes through ScreenCaptureKit with `SCCaptureDynamicRange::HDRLocalDisplay` when `hdr::supported()` (Apple Silicon, macOS 15), and Windows only opens a `dxgi::Session` when the output is composited in HDR mode. Either platform decodes its extended-range frames into a linear scRGB `HdrImage`, and when neither can, the session simply delivers `FrameData::Sdr` and the ordinary H.264 sink records normally. The sink is chosen from the first frame (`video::open`): `FrameData::Hdr` goes to `HdrMp4Sink`, and if the HEVC encoder refuses it the half-written file is deleted and an H.264 SDR sink starts over from scratch, so a failure costs quality, never the recording. `video::hdr` converts scRGB to BT.2020 nits via `reference_white_nits()`, runs PQ through a table indexed by `sqrt(nits / 10000)`, and writes 10-bit MSB-aligned codes (`code << 6`) into 4:2:0 planes (2×2 chroma mean); bands above 256K pixels split across up to 8 threads. **On macOS the AVAssetWriter compression settings must include `AVVideoProfileLevelKey = "HEVC_Main10_AutoLevel"`** (`kVTProfileLevel_HEVC_Main10_AutoLevel` from VTCompressionProperties.h): with only the 10-bit `kCVPixelFormatType_420YpCbCr10BiPlanarVideoRange` buffers and `AVVideoColorPropertiesKey`, VideoToolbox accepted the frames and still wrote an 8-bit Main stream (`profile_idc` 1, both SPS bit depths 0), which no player treats as HDR. The colour properties (ITU_R_2020 / SMPTE_ST_2084_PQ / ITU_R_2020) are what make the muxer write the `colr` box. Windows drives Media Foundation with `eAVEncH265VProfile_Main_420_10` and P010 input (64-byte row stride); its muxer writes no `colr` and the encoder leaves the colour description out of the VUI, so `video::mp4_colour::insert` appends an `nclx` box (BT.2020 / PQ / BT.2020, video range) to the finished file by rewriting only the tail after `mdat` — it refuses any file whose sample data follows `moov`, and a failure is logged without discarding the recording. The ignored `hdr_sink` tests on both platforms encode synthetic frames and assert the Main10 profile, 10-bit SPS depths and the `colr` box; they are the only check available on a machine without an HDR display, because the capture side needs a real HDR-mode desktop.
- **MP4 closing timestamps must strictly increase.** `finish` appends a final held sample; `end - 1 ms` can land on the same CMTime tick (timescale 600) as the last sample on very short recordings, which makes `AVAssetWriter finishWriting` fail with "The operation could not be completed" — use `at + 2 ms` as the floor. Both macOS and Windows sinks keep the already-scaled frame in `last` instead of cloning the full-resolution capture, and `finish` must not scale it again.
- **`events::install()` must run before `Application::run`.** Both `global-hotkey` and `muda` keep their event handler in a `OnceLock` that their first `send()` initialises to `None`; after that, `set_event_handler` silently fails and events go to a channel nobody reads. Registering from `main()` before the hotkey manager and tray icon exist is the only safe ordering. Callbacks only push into the bus — GPUI state is `!Send` and must stay on the main thread. `muda` is used only by `tray-icon` here, so a global menu handler cannot steal GPUI's own menu events.
- **During a recording, a hotkey stops it and queues its own action** (`Controller::queued_capture`), which runs after encoding clears `busy`. `Controller::fail` clears the queue so actions never chain onto a failure.
- **`gpui_kit::open_window` via `cx.defer`** when the caller still holds `Controller` (or any entity the new view will `read`). `open_window` renders immediately. Overlays are opened after `CaptureSession` exists and the controller update that created it has ended; panel/pin/tray attach already defer.
- **`KeyBinding` rejects `secondary-`.** Use `crate::shortcut!("c")` (`cmd-` / `ctrl-`), never `secondary-c`.
- Keep `cargo check --workspace`, `cargo build`, and `cargo clippy --workspace --all-targets -- -D warnings` clean.

## Config and data

`AppDirs` (`crates/store/src/paths.rs`) uses `directories::ProjectDirs::from("dev", "SnapIt", "SnapIt")`. `SNAPIT_HOME` puts config and data in one directory. Discover failure falls back to `$TMP/snapit`.

| File | macOS | Windows |
| --- | --- | --- |
| `config.toml` | `~/Library/Application Support/dev.SnapIt.SnapIt/config.toml` | `%APPDATA%\SnapIt\SnapIt\config\config.toml` |
| History | `…/dev.SnapIt.SnapIt/history/` | `%APPDATA%\SnapIt\SnapIt\data\history\` |

`[update]` holds `check` (background check on launch, default true) and `last_check` (Unix time; automatic checks are at most once per 24 h). It is written whenever a check starts, so a hand-edited file only needs `check`.

`[recording]` holds `fps` (1–30), `max_duration_secs` (0 = unlimited, max 600), `last_format` (`gif`/`mp4`), `captures_cursor` (default false; macOS-only, since Windows DXGI never includes the pointer) and `hdr` (default true; MP4 only — falls back to the ordinary SDR/H.264 sink when the display is not in HDR mode or the 10-bit HEVC encoder is unavailable).

Corrupt TOML is moved to `config.toml.bak` and replaced with defaults. OCR models (non-macOS): `$SNAPIT_OCR_MODELS`, `models/` next to the binary, then `~/.snapit/models`.

UI strings come from rust-i18n: `crates/app/locales/{en,zh-CN}.yml` (flat dotted keys, `%{name}` placeholders, `_version: 1`, both files must keep the same keys). `#[macro_use] extern crate rust_i18n;` and `rust_i18n::i18n!("locales", fallback = "en");` must stay at the crate root (`main.rs`) because `t!` expands to `crate::_rust_i18n_t!`. `general.language` is `auto` (sys-locale; zh* → `zh-CN`, else `en`) or an explicit locale. Switching it at runtime re-renders windows, relabels the tray, and rebuilds app menus and open panel titles.

## Build, test, smoke

```bash
cargo check --workspace --all-targets
cargo build                 # binary: snapit
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace      # store persistence/prune, hotkeys, tray icon bytes
cargo run -p snapit                 # tray + hotkeys only (no launcher window)
cargo run -p snapit -- --capture    # also --settings --history --background
```

Examples: `snapit-capture` `capture_once`, `snapit-ocr` `ocr_image`, `snapit-recorder` `record_gif`. Launch is tray + hotkeys only (`QuitMode::Explicit`, macOS Accessory). A lock file in the data directory keeps one instance (`instance.rs`): a second launch without flags logs and exits; `--capture` / `--settings` / `--history` are written to `snapit.request`, polled by the owner every 50 ms and posted onto the event bus, so CLI actions are never dropped. Stale requests are removed when the lock is acquired. There is no home/launcher window; OCR opens a small results panel. macOS screen capture needs Screen Recording permission on the host Terminal/IDE.

`[profile.dev] opt-level = 1` (workspace crates; dependencies stay at 2) keeps `cargo run` interactive — the overlay repaints on every pointer move, and `-O0` makes that visibly slower. Do not drop it back to 0.

macOS `.app` (does not replace `cargo run -p snapit`):

```bash
./scripts/bundle-macos.sh                  # prefers an already-built debug binary
./scripts/bundle-macos.sh --bin path/to/snapit
./scripts/bundle-macos.sh --target aarch64-apple-darwin --out dist   # CI / release
```

Output: `target/macos/SnapIt.app` (or `--out dist` → `dist/SnapIt.app`). Bundle id `dev.SnapIt.SnapIt` (same as `AppDirs`). Ad-hoc signed (`codesign --sign - --force --deep`). Rebuilds change the code signature; Screen Recording may need to be re-granted.

macOS DMG follows SwitchHostsLite (not create-dmg): `scripts/package-macos.sh` writes `dist/SnapIt-<version>-macos-<arch>.{dmg,zip}` (`ditto` zip, `hdiutil` ULMO + `/Applications` symlink, retries on "Resource busy"). Developer ID / `notarytool` / `stapler` use the same secret names as SwitchHostsLite (`MACOS_CERTIFICATE`, `MACOS_CERTIFICATE_PASSWORD`, `MACOS_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD`). Missing secrets keep the ad-hoc signature and still emit the DMG; do not fail and do not invent certificates.

Windows setup: `./scripts/bundle.sh windows|all` (`scripts/bundle-windows.sh`) compiles `scripts/windows/snapit.nsi` with NSIS (`makensis`, or `MAKENSIS=/path`). Output: `dist/SnapIt-<version>-windows-<arch>-setup.exe` (all users, `Program Files\SnapIt`; setup prompts to close a running SnapIt and reuses the last install directory) plus the staged `dist/windows/SnapIt/SnapIt.exe`. `--target` defaults to the host triple on Windows (the MSVC triple elsewhere); a missing Rust target, linker or NSIS prints `skip:` and exits 0 — do not install cross compilers from these scripts. `dist/` is gitignored.

Release packaging is `.github/workflows/release.yml`, matching SwitchHostsLite: `v*` tags or `workflow_dispatch` with that tag. It checks the tag against `[workspace.package] version`, installs the `rust-toolchain.toml` pin (1.99.1; do not float to stable), `rustup target add`, then a 4-target matrix (`macos-aarch64`, `macos-x86_64` cross-compiled on `macos-latest`, `windows-x86_64`, `windows-aarch64` cross-compiled on `windows-latest`). macOS: `scripts/bundle-macos.sh --target … --out dist` then `scripts/package-macos.sh --name SnapIt-<version>-<key>`. Windows: the job installs NSIS if the image lacks it, then `scripts/bundle-windows.sh --bin … --target … --setup-out out`. Artifacts: `SnapIt-<version>-macos-<arch>.{dmg,zip}`, `SnapIt-<version>-windows-<arch>-setup.exe`, `latest.json`, `SHA256SUMS.txt`. `scripts/release-manifest.py` writes the manifest; the macOS DMG (`macos-<arch>-dmg` key, preferred by the app), the macOS zip (fallback) and the Windows setup.exe are the updater packages. A GitHub Release is created for the tag. macOS sign/notarize/staple only when the SwitchHostsLite secrets are present. `.github/workflows/ci.yml` runs `cargo test --locked` and clippy on macOS and Windows.

Updates follow SwitchHostsLite too. `releases/latest` skips pre-releases, so the app lists releases itself: `GET https://api.github.com/repos/<repo>/releases?per_page=20`, take the highest parsable tag carrying a `latest.json` asset (drafts skipped, pre-releases kept), and fall back to `releases.atom` + `releases/expanded_assets/<tag>` when the anonymous API is rate-limited. The repo comes from `SNAPIT_UPDATE_REPO` at build time (set by the workflow), else `repository` in `Cargo.toml`; with neither, the update UI says updates are not configured instead of pretending to check. Auto-check runs 5 s after launch when `[update] check = true` (default) and the last check was over 24 h ago; finding a newer version opens the update window, and a stable build moving to a pre-release asks once before downloading. `SNAPIT_UPDATE_MANIFEST_URL` is a debug-build override for a local server.

Downloads are staged beside their target (`.part` then rename) and a package that fails the size/SHA-256 check is deleted, so nothing unverified is ever left looking installable. macOS only fetches the DMG into `~/Downloads` and reveals it in Finder — replacing a running app is left to the user, and the bundle-patching code was removed for that reason, so do not reintroduce it. Windows copies itself to `%TEMP%` as an update helper, waits for the app to exit, runs the setup with `/S` elevated and restarts. The installer kills a running SnapIt with `taskkill` (after a prompt when interactive, directly under `/S`), so do not add in-app state that is only flushed on a normal quit. Before tagging a release, run the ignored `simulate_update` test against a locally served manifest: `SNAPIT_TEST_MANIFEST_URL=… cargo test simulate_update -- --ignored` (`SNAPIT_TEST_CURRENT` overrides the running version).

`QuitMode::Explicit`: closing settings / history / OCR panel / pin / overlay does not quit; tray **退出** or `⌘Q`/`Ctrl+Q` does. The Dock icon appears only while a panel (settings / history / OCR / permissions / update) is open; overlays, the recording bar, and pins stay Dock-less. Legacy `open_window_on_launch` and `show_dock_icon` in `config.toml` are ignored and stripped on load.

## Stubbed or limited

- **Window snap** (`crates/capture/src/windows.rs`): on-screen window rects are snapshotted at freeze time, front-to-back — macOS `CGWindowListCopyWindowInfo`, Windows `EnumWindows` + DWM extended frame bounds. Fullscreen apps can split one visual window into several platform windows (Chrome: tab strip, toolbar, content); `SessionFrame::window_at` (`session.rs`) merges touching same-process windows that line up on an axis and cover the display, so the wheel reaches the whole app. Accessibility element chains (`elements_at` in `snapit-capture`) run on the background executor via `ElementQuery` / `PendingHover`: the window highlight shows immediately and the element chain replaces it when the lookup lands, with a generation guard dropping stale results. Toggle: `capture.window_snap` (default on).

- **Windows.Media.Ocr** (`crates/ocr/src/windows_ocr.rs`) uses one recognizer language (`TryCreateFromLanguage` when the setting is supported, else user-profile languages). Needs an installed OCR language pack; no per-line confidence; `engine_with` falls back to ocrs if WinRT creation fails.
- **ocrs** is Latin-only; the OCR language setting applies to macOS Vision and Windows.Media.Ocr.
- **GIF pin** uses the PNG thumbnail (`HistoryStore::pin_source`), not a GIF decoder (`image` features are `png`+`jpeg` only).
- **Recording cursor and bar exclusion**: ScreenCaptureKit filters by window object, so the recorder drops every on-screen `SCWindow` owned by SnapIt's own process; the overlay and the bar are excluded even when the bar sits over the region (pins are left out too, since they are SnapIt windows). `open_recording_bar` still prefers placing the bar outside the selection, but the user may drag it anywhere. The dim mask and border sit outside the captured bounds, so they never show in the recording either. Windows excludes both windows with `WDA_EXCLUDEFROMCAPTURE`, but DXGI never includes the pointer, so `captures_cursor` only does something on macOS.
- **Annotations** live on the frozen overlay (`crates/app/src/annotate.rs`, wired through `session.rs` / `overlay.rs`): rectangle, arrow, pen, mosaic, text, numbered steps; GPUI canvas while editing; tiny-skia bake (real mosaic pixelation) on Copy / Save / Pin. Undo is Cmd/Ctrl+Z; OCR/GIF use the unbaked crop. Text bake uses a system font when one is found, else 5×7 digits.
- **Multiple regions** (`session.rs` `collecting`, Xnip-style): holding `Shift` enters collect mode — hovering lights the target, clicking or dragging adds a region, clicking an existing region removes it (danger border, bottom-left hint). Releasing `Shift` composes same-display regions into one selection (`Composed`): the toolbar and annotations work on the combined image, Copy / Save / Pin / OCR use it, resizing and GIF recording are disabled, and pressing `Shift` again restores the original regions for further edits. The modifier listener is registered per element via `div().on_modifiers_changed` because `Window::on_modifiers_changed` panics outside the paint phase. Regions on the same display keep their on-screen positions over a transparent canvas (`compose_at_positions`); a collection spanning displays keeps the separate-region behavior and is stitched top-to-bottom (`stitch_vertical`) without annotations.
- **Tray** `MenuEvent` and `GlobalHotKeyEvent` arrive through callbacks registered in `events::install()` (no polling). Create the icon on the GPUI main thread after launch (`tray::init` defers).
- Unbundled binary process name is **`snapit`** (`cargo run -p snapit`); system notifications are disabled outside an app bundle. Local macOS bundle: `scripts/bundle-macos.sh` → `target/macos/SnapIt.app` (`dev.SnapIt.SnapIt`, ad-hoc signed); distribution DMG/zip: `scripts/package-macos.sh`. Windows setup: `scripts/bundle.sh` (NSIS, all users). No `.msi`.

## How to extend

**New global hotkey**

1. Field on `snapit_store::Hotkeys` (`crates/store/src/config.rs`).
2. Variant on `HotkeyAction` (`hotkey.rs`): `ALL`, `label`, `binding`, `set_binding`. Settings fields come from `ALL`.
3. Branch in `Controller::on_hotkey`. Syntax is `global-hotkey` (`Alt+Shift+A`); empty string disables.

**New selection toolbar action**

1. `SessionCommand` in `session.rs`.
2. `Controller::handle_command` in `controller.rs`.
3. Button + `actions!` in `overlay.rs`; bump `TOOLBAR_WIDTH`. Optional `CaptureIntent` if it should run as soon as the region is committed.

**New UI string**

1. Add the key to both `crates/app/locales/en.yml` and `zh-CN.yml` (same key set).
2. Use `t!("group.key")` in code; it returns `Cow<str>`, so call `.to_string()` for `SharedString` / gpui `IntoElement` parameters.

**New OCR backend**

1. `impl OcrEngine` under `crates/ocr/src/`.
2. Select it in `engine_with` (`crates/ocr/src/lib.rs`). Changing OCR settings calls `Controller::reset_ocr_engine`.
